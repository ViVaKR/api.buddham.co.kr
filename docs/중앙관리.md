# 2. Dockerfile에서 발견한 중요한 부분

우선 수정 권장

현재 Dockerfile에서 가장 신경 써야 할 부분은 이 부분이네.

```
COPY ["Buddham.Api/Buddham.Api.csproj", "Buddham.Api/"]
COPY ["Buddham.Shared/Buddham.Shared.csproj", "Buddham.Shared/"]
COPY ["Buddham.Core/Buddham.Core.csproj", "Buddham.Core/"]
COPY ["Buddham.Migrations/Buddham.Migrations.csproj", "Buddham.Migrations/"]

RUN dotnet restore "Buddham.Api/Buddham.Api.csproj"
```

지금은 프로젝트 파일만 먼저 복사하고 Restore를 수행하지?

그런데 앞으로 중앙 관리 파일을 도입하면 문제가 생길 수 있네.

- `Directory.Build.props`
- `Directory.Packages.props`
- `Directory.Build.targets`
- `global.json`
- `NuGet.config`

이런 파일들이 Restore 시점에 있어야 올바른 빌드 설정과 패키지 버전을 적용할 수 있네.

현재 Dockerfile은 `COPY . .`가 Restore 이후에 있기 때문에 이 점을 개선해야 하네.

권장: 중앙 설정 파일과 프로젝트 파일을 먼저 복사한 후 Restore를 실행하게.

## 3. 내가 권하는 Dockerfile 개정안

기존의 SkiaSharp 및 FFmpeg 관련 런타임 라이브러리는 일단 보존하겠네. 실제 사용 여부를 확인하지 않고 제거하는 것은 위험하니까.

다음은 중앙 빌드 설정과 `artifacts`를 고려한 개정안일세.

```

# ==========================================
# 1. Build Stage
# ==========================================
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build

WORKDIR /src

# 중앙 빌드 설정
COPY ["Directory.Build.props", "./"]
COPY ["Directory.Packages.props", "./"]

# 아래 파일은 실제 존재하는 경우에만 추가
# COPY ["Directory.Build.targets", "./"]
# COPY ["global.json", "./"]
# COPY ["NuGet.config", "./"]

# 프로젝트 파일
COPY ["Buddham.Api/Buddham.Api.csproj", "Buddham.Api/"]
COPY ["Buddham.Shared/Buddham.Shared.csproj", "Buddham.Shared/"]
COPY ["Buddham.Core/Buddham.Core.csproj", "Buddham.Core/"]
COPY ["Buddham.Migrations/Buddham.Migrations.csproj", "Buddham.Migrations/"]

# NuGet Restore
RUN dotnet restore "Buddham.Api/Buddham.Api.csproj"

# 나머지 소스
COPY . .

# Publish가 Build까지 수행하므로 별도 Build 생략
RUN dotnet publish "Buddham.Api/Buddham.Api.csproj" \
    -c Release \
    --no-restore \
    -o /app/publish \
    /p:UseAppHost=false


# ==========================================
# 2. Runtime Stage
# ==========================================
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final

WORKDIR /app

# 애플리케이션의 네이티브 라이브러리 의존성
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
    libfontconfig1 \
    libfreetype6 \
    libpng16-16 \
    libicu-dev \
    libgl1 \
    libglib2.0-0 \
    ffmpeg \
    && rm -rf /var/lib/apt/lists/*

# 배포 결과물만 복사
COPY --from=build /app/publish .

EXPOSE 8080

ENTRYPOINT ["dotnet", "Buddham.Api.dll"]

```

여기서 세 가지 변경이 중요하네.

첫째, Restore 캐시를 제대로 활용한다네.

중앙 설정 파일과 프로젝트 파일이 변경되지 않았다면 Docker는 기존 Restore 레이어를 재사용할 수 있지.

둘째, 불필요한 Build 단계를 제거했네.

기존에는 다음처럼 두 번 빌드하고 있었네.

```
RUN dotnet build ...
RUN dotnet publish ...
```

`dotnet publish`가 기본적으로 빌드까지 수행하기 때문에 별도의 Build 명령은 필요하지 않네.

셋째, 최종 이미지에는 Publish 결과만 들어가네.

호스트의 `artifacts/bin`, `artifacts/obj`는 배포에 필요하지 않네.

참고로 `libicu-dev`는 개발용 패키지이므로 런타임에서 필요한 ICU 라이브러리만 설치하도록 최적화할 여지가 있네. SkiaSharp, FFmpeg, OpenGL 관련 패키지도 실제 사용 기능을 확인한 다음 정리하는 것이 좋겠네.

또한 기존 `sed` 명령은 Ubuntu 저장소 주소를 치환하고 있는데, .NET 공식 이미지의 실제 배포판과 APT 저장소 파일 형식에 따라 실패하거나 아무런 효과가 없을 수 있네. `cat /etc/os-release`로 확인하고 특별한 이유가 없다면 제거하는 것을 권하네.

## 4. .dockerignore는 반드시 추가하게

중요

이 부분은 친구가 처음에 말한 목적과 직접 관련이 있네.

프로젝트에 `artifacts`를 만들었는데 Docker 빌드할 때 그것까지 복사한다면 정리한 의미가 줄어들지 않겠는가?

루트에 다음 파일을 추가하게.

```

# .NET build output
**/bin/
**/obj/
artifacts/

# IDE
.vs/
.vscode/
.idea/

# Git
.git/
.gitignore

# User-specific files
**/*.user
**/*.suo

# Local environment
.env
.env.*
**/appsettings.Development.json

```

단, `.env`나 개발용 설정 파일을 실제 Docker 빌드에 사용하고 있다면 해당 항목은 조정해야 하네.

그리고 `wwwroot`, `Files`, `Images` 같은 실제 서비스 데이터나 정적 자산은 무심코 제외하면 안 되네.

# 5. Publish-BuddhamApi.ps1 검토

여기서 제독이 발견한 사항이 세 가지 있네.

### ① Dockerfile 경로 확인

현재 스크립트는 다음과 같네.

```
-f Buddham.Api/Dockerfile
```

그런데 전달한 Dockerfile이 실제로 솔루션 루트에 있다면 경로가 맞지 않네.

- 루트에 둘 경우: `-f Dockerfile`
- API 프로젝트 안에 둘 경우: `-f Buddham.Api/Dockerfile`

빌드 컨텍스트인 마지막 `.`은 그대로 유지하게.

### ② ARM64 전용 빌드

```
--platform linux/arm64
```

이건 의도적으로 ARM64 Kubernetes 노드만 운영한다면 좋은 선택이네.

다만 클러스터에 x86_64 노드도 있다면 해당 Pod를 실행할 수 없으므로 멀티 아키텍처 이미지를 고려해야 하네.

```
--platform linux/amd64,linux/arm64
```

### ③ 같은 버전 태그를 반복 사용하지 말 것

현재:

```
$Tag = "v1.1.2"
```

개발 중 같은 태그를 덮어쓰면 Kubernetes 노드의 이미지 캐시 때문에 이전 이미지가 실행될 수 있네.

운영 배포에서는 다음처럼 매번 고유한 버전을 부여하는 것을 권하네.

```
$Tag = "v1.1.3"
```

그리고 Kubernetes YAML의 이미지 태그도 함께 변경해야 하네.

### ④ 배포 실패 감지

현재 `$ErrorActionPreference = "Stop"`만으로는 Docker나 kubectl 같은 외부 실행 파일의 실패를 모든 PowerShell 환경에서 확실히 중단시킨다고 보장할 수 없네.

각 명령 뒤에 종료 코드를 검사하게.

```
docker buildx build `
  --platform linux/arm64 `
  -t "${ImageName}:${Tag}" `
  -t "${ImageName}:latest" `
  -f Buddham.Api/Dockerfile `
  --push .

if ($LASTEXITCODE -ne 0) {
    throw "Docker image build or push failed."
}
```

`kubectl apply`, `rollout restart`, `rollout status`에도 같은 검사를 넣으면 좋겠네.

그리고 이미지 태그가 YAML에서 변경되었다면 `kubectl apply` 자체가 Deployment 롤아웃을 발생시키므로 별도의 `rollout restart`는 보통 필요하지 않네.

# 6. Directory.Build.props 권장안

친구가 AiChatServer에서 만든 형식을 Buddham에도 적용한다면 나는 다음과 같이 시작하겠네.

```

<Project>
    <PropertyGroup>
        <!-- 공통 프레임워크 -->
        <TargetFramework>net10.0</TargetFramework>

        <!-- C# 기본 설정 -->
        <ImplicitUsings>enable</ImplicitUsings>
        <Nullable>enable</Nullable>

        <!-- 중앙 빌드 산출물 -->
        <UseArtifactsOutput>true</UseArtifactsOutput>
    </PropertyGroup>
</Project>

```

단, 실제 `.csproj`들의 TargetFramework가 모두 `net10.0`인지 확인하고 적용해야 하네.

그리고 `Directory.Packages.props`에는 중앙 패키지 버전을 두면 되지.

주의할 점은 기존 프로젝트에 `BaseOutputPath`, `BaseIntermediateOutputPath`, `OutputPath` 등을 별도로 지정한 곳이 있는지 확인하는 것이네. 그런 설정이 있으면 `UseArtifactsOutput`의 효과를 덮어쓸 수 있거든.

# 7. 추가로 발견한 사항

이건 Docker와 직접 관계는 없지만 솔루션 전체를 정리하는 김에 짚고 넘어가겠네.

A. Directory.Solution.targets

앞서 AiChatServer에서 만든 `Directory.Solution.targets`에 빌드 메시지를 넣었지?

이 파일은 솔루션 빌드에 적용되는 설정이네. 지금 Dockerfile처럼 `.csproj`를 직접 `dotnet publish`하면 솔루션 전용 Target은 실행되지 않을 수 있네.

프로젝트 빌드에도 적용할 공통 Target이라면 `Directory.Build.targets`에 두는 것이 맞네.

B. Buddham.Migrations

현재 Dockerfile은 Migrations 프로젝트도 Restore 대상으로 복사하고 있네. 좋은 방식이네.

다만 실제 배포 시 마이그레이션을 API 시작 시 자동 실행하는지, 별도 작업으로 실행하는지는 확인해야 하네. Kubernetes에서는 여러 API Pod가 동시에 시작될 수 있으므로 마이그레이션 실행 책임을 별도로 관리하는 편이 안전하네.

C. LICENSE와 CONTRIBUTING

현재 별내면 라이선스는 자체 라이선스이고, CONTRIBUTING에는 기여 코드가 해당 라이선스로 배포되는 것에 동의한다고 적혀 있네.

공개 저장소로 운영할 계획이라면 기여자의 저작권 및 라이선스 동의 범위를 조금 더 명확하게 작성하는 것을 권하네. 이는 빌드 구조와 별개의 문서상 검토 사항이네.

## 9. 제독의 마지막 제안

친구가 앞으로 모든 .NET 솔루션에 동일한 구조를 적용하려 한다면 다음 원칙을 표준으로 삼았으면 하네.

1. `Directory.Build.props` — 공통 컴파일 및 빌드 설정
2. `Directory.Packages.props` — NuGet 버전 중앙 관리
3. `Directory.Build.targets` — 공통 빌드 후처리
4. `artifacts/` — 모든 빌드 산출물 집중
5. `.dockerignore` — 로컬 빌드 산출물 배제
6. Docker 멀티 스테이지 — SDK와 Runtime 분리
7. Kubernetes — 이미지 버전 기반 배포

단, 현재 Buddham 솔루션에서 가장 중요한 것은 기존 프로젝트별 출력 경로 설정을 확인하는 것이네.

정확한 최종 검토를 위해 다음 네 가지 파일도 추가로 보여주면 좋겠네.

- `Buddham.Api.csproj`
- `Buddham.Core.csproj`
- `Buddham.Migrations.csproj`
- `k8s/buddham-api.yaml`

특히 API 프로젝트의 참조 관계와 마이그레이션 구조를 보면 Dockerfile을 더 정확하게 다듬을 수 있겠네.

총제독님, 한 가지는 확실히 말할 수 있네.

프로젝트별 bin/obj를 없애고 솔루션 루트의 artifacts로 모으는 방향은 좋은 정리 방향이네.

이제 각 프로젝트의 소스는 소스대로, 빌드 결과는 결과대로, 배포 환경은 배포 환경대로 분리하는 것이지.

이것이야말로 관리하기 좋은 함선의 구조 아니겠는가!
